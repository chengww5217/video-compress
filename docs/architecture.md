# 架构与工作原理

## 边界：只换编码，不动画面

这个工具做的事情只有一件——**把同一幅画用更高效的编码器压得更小**。所以下面这些"看起来能省更多"的做法都不在范围内，哪怕它们的体积收益更大：

- 不裁黑边、不缩放（比如把放大过的 1080p 降回 720p）、不改帧率、不反交错
- 不做降噪 / 去色带 / 去块之类的"修片源"，源片的瑕疵会被忠实保留
- 不用 AV1 的颗粒合成（体积收益很大，但合成的颗粒逐帧不对应，等于换掉了画面）

唯一两处画面级的改动都是编码本身需要的：位深提到 10-bit（编码器内部精度，解码回来仍是同一幅画），以及源色度格式编码器不支持时的必要降级（如 libsvtav1 只吃 4:2:0）。音轨、字幕、章节、附件、色彩与 HDR 元数据都尽量原样保留。

"视觉无损"在这里有明确的操作化定义，不是形容词：**VMAF ≥ `target_vmaf`（默认 95，取多段里的最差段）+ 每段不低于 `vmaf_min_segment` + 色彩/HDR 元数据与源一致**。三条都过才算过。

## 工作流程

```
扫描视频 → ffprobe 探测 → 是否需要压缩？ ──否──→ 跳过（记录原因）
                │是
                ▼
       自适应 CRF 搜索（多段抽样 + VMAF 二分，0.25 级粒度）
                ▼
       按样本码率预估体积 → 收益不够就跳过（不白编几小时）
                ▼
       编码到 <源文件名>.tmp.mkv
                ▼
       校验：时长 / 分辨率 / 流数量 / 体积 / 色彩与 HDR / 解码 / VMAF 抽检
                │通过                    │失败
                ▼                        ▼
       替换并删除原文件          删除临时文件，保留原件，记录日志
```

`--remux` 模式把第一关的「否」分支接到[重封装](#重封装模式)的重编流程上，「是」分支照常压缩但收紧 keyint。

## 防重复压缩的三道保险

1. 已处理文件会写入 `COMMENT=<tag_marker>-v1` 元数据标记（默认 `vcompress-v1`），再次遇到直接跳过；标记名跟着 `[skip].tag_marker` 走，改配置检测也随之变化。原有的 comment 会被保留，标记追加在后面（`原注释 | vcompress-v1`）；
2. 按编码器与「每像素码率」（BPP = 视频轨码率 ÷ 宽 × 高 × 帧率）判断是否已压到位。只算视频轨，容器没给就用总码率扣掉音轨估算，避免肥音轨把判断带偏；
3. 预估收益低于 `min_saving_ratio`（默认 15%）的不压；实际收益低于 5% 的丢弃结果、保留原件。

自适应搜索结束后还会再拦一道：拿样本在选定 CRF 下的实测码率推算全片体积，收益仍不到 `min_saving_ratio` 就直接跳过，不会白编几个小时最后被 5% 的门槛丢掉。这个预估比 `expected_ratio` 那张按编码器写死的表准得多（合成片源上实测误差 0.03%，真实片源会大一些）。同理，连 `crf_min` 都达不到 `target_vmaf` 的片源（通常是重颗粒片）默认也直接跳过——「视觉无损优先」的前提下，压出一个低于目标画质的产物没有意义；想照压可以设 `[adaptive] require_target = false`。

另外 `logs/results.jsonl` 会记录每次运行结果，重跑时自动跳过上次已压缩（`ok`）和已跳过（`skipped`）的文件。跳过前会比对体积：同名文件被换成另一个片源时旧记录不再生效，会重新检查。**缓存按模式区分**：记录里带 `mode` 字段（`compress`/`remux`），上次压缩过的文件重封装模式照样要重新处理，反过来也一样；老记录（没有这个字段）按压缩模式算。

**失败分两种，重跑待遇不同**：磁盘满、被 OOM 杀掉、量不出 VMAF 这类是环境问题，换个时间重试有意义，所以照常重跑；而「产物没比源文件小」「实际只省了 3%」这个结论只取决于片源和编码配置，重跑必然还是同一个数——这种记 `"permanent": true`，下次直接跳过，不再花几小时算同一个答案。想再试一次（换了编码器、调了 `target_vmaf`、升了 ffmpeg）加 `--force`。

这条和编码前的收益门槛是同一个判断的两端：那边靠样本外推提前跳过，这边量的是真产物。样本外推有 ±25% 的误差（实测），贴着门槛的文件仍会漏过去、编完才被判出局，所以两边的结论都得让文件下次别再来一遍。

## 重封装模式

`--remux` 把「检测不用再压」的文件按 `[encode]` 配置的编码器重编视频轨，keyint 绑定到 `max_keyframe_gap_s`，修快进卡顿。

**不做体检**。以前先扫全片关键帧，间隔没超上限就放过，avi/flv/wmv/mpg 则流复制换容器。在 Windows 播放机（PotPlayer，RTX 3060 Ti）上的实测推翻了这个判据：关键帧间隔 4.17s 的 h264 原片快进打 1 分（满分 5），重编成 5s 间隔的 AV1 打 4 分；ffmpeg 量出的原片精确跳转最坏也只要 250–340ms，和体感的「画面 2s 才响应」差一个数量级。量出来的间隔和卡不卡对不上，按它筛只会把该修的文件放过去，所以现在一律重编，流复制那条路也一起去掉了。

流程（`remux.py` 生成参数，`pipeline.py` 编排）：

```
元数据里已有重封装标记？ ──是──→ 跳过（修过了）
交错源？                  ──是──→ 跳过（重编码会丢交错标记）
should_skip 说「不用再压」？ ──否─→ 正常压缩，但 keyint 绑定到间隔上限
                 │是
                 ▼
   重编视频轨：keyint = 帧率 × 间隔上限，音轨/字幕原样复制
   CRF 按 VMAF 98 搜索，达不到 / 预估涨幅超 10% 就放弃不动
```

和压缩模式的三个口径差异：

- **画质闸门更严**（VMAF 98 vs 95）：重编码是二次编码，两代损失叠加，必须留代际余量。连 `crf_min` 都达不到 98 就不动这个文件——为了修快进把画质压坏是本末倒置。搜索失败也不回退固定 CRF：压缩模式回退了顶多画质差点，这里等于拿一个没量过画质的二次编码去替换原本完好的文件
- **体积闸门反向**（允许最多涨 10%，压缩是必须至少省 15%）：关键帧不免费，多出来的 I 帧就是修快进的体积代价。编码前按样本码率预估，超限直接跳过；编码后实测超限同样判「永久失败」（这个结论重跑也一样）
- **音轨一律复制**：重封装的承诺是「只动该动的」

重编完成后会**扫一遍产物的关键帧**：编码器没兑现 keyint 承诺（产物最长间隔仍超标）就判失败，不交付「修了但没修好」的产物。源文件不扫。

产物打 `vcompress-remux-v1` 标记（含普通标记，所以普通模式自动跳过它们）；重封装模式自己认这个更具体的标记，不会重编两遍。输出名沿用编码产物规则，但源名已带同一编码器后缀时先摘掉再补（`a.av1.mkv` 不会叠成 `a.av1.av1.mkv`）。

旧版体检留在 `results.jsonl` 里的跳过记录（「关键帧间隔与容器都没有问题」「扫关键帧失败」等）在新规则下不成立，`ResultStore.is_cached` 按原因前缀认出来，不算缓存命中；画质/体积闸门的跳过结论和体检无关，照旧缓存。

## 自适应 CRF 搜索

对每个视频从整片均匀抽 `sample_count`(4) 段、每段 `sample_seconds`(10) 秒，用 VMAF 二分搜索「满足目标画质的最小码率」对应的 CRF：

- 一个 CRF 的成绩取**最差段**，不取平均：平均分能被好段抬起来，观感却是最差处决定的。某段已经不达标时后面的段直接不量，省时间
- 只看中点一段是不够的：那个位置可能正好是明亮的动作戏或全黑的过场，按它定的 CRF 拿到暗场就不成立了。铺开取样后，搜索和后面用多段抽检的校验才是同一个口径
- `search_step = 0.25`：搜索按 0.25 级 CRF 走，不是整数。本机实测 1 级 CRF ≈ 8% 体积、0.25 级 ≈ 2%，只搜整数等于平均白扔半级 ≈ 4% 的体积，而画质闸门一点没变
- `target_margin = 0.05`：录取线是 `target_vmaf + target_margin` 而不是 `target_vmaf` 本身。几段十来秒的样本外推到一两小时的全片有 ±0.5 分的波动，贴线（95.02 vs 95.0）的 CRF 一旦没收，全片抽检跌破目标就是大概率事件——宁可降一档多费一点体积，也不把宝押在抽样运气上

## 校验

### 解码校验的源文件基线

解码校验问的不是"产物解码有没有报错"，而是"编码有没有引入新的损坏"。这两个问题在片源本身有瑕疵时会得出相反的答案：AVI 按固定块存 MP3，块边界不保证和 MP3 帧边界对齐，损坏或拼接过的片源里会出现没有合法帧头的包；音轨判定为 `copy` 时这些包原样搬进 MKV，解码器照样报 `Header missing`。只看产物就会把一个完全正常的编码结果丢掉，而且下次重跑还在同一处翻车——解码失败不进缓存（它可能是环境问题），所以每次都要重烧一遍编码时间。

所以产物报错时会再解一遍源文件做基线，只有源文件里没有的报错才算产物的问题。三个细节：

- **惰性**：产物解码干净就不碰源文件，正常流程零额外开销。只有已经要判失败时才多花一次源文件全量解码（1080p 一小时片源约几十秒，相对动辄几小时的编码可以忽略）
- **单向**：源文件的全量解码会多出产物不可能有的噪音（容器层的 dts 告警、老编码器的 flag 修正），那些不算问题
- **归一化**：比对前抹掉每次运行都不同的对象地址（`[mp3float @ 0x5f34…]`）和流序号（同一条音轨在 AVI 里是 `0:1`、在产物里可能是 `0:0`），并把 ffmpeg 的 `Last message repeated N times` 展开成次数。消息里仍带解码器名，所以视频和音频的错不会混为一谈；同一条消息在产物里出现得比源文件多，也算新问题

基线兜不住的一类是**音频时间戳的毫秒取整**。mkv 的时间戳只精确到毫秒，拼接过的 mp4 在接缝处常有只占 1 个采样的 AAC 包，copy 进 mkv 后几个包挤到同一毫秒上；解码时 ffmpeg 按采样重建时间戳，得到相等或倒退几个采样的值，`-f null` 要求 dts 严格递增，于是报 `non monotonically increasing dts`。源文件的时间基是 1/采样率，同一处根本不报，比对时这些行全成了"新问题"。所以比对前先把它们去掉：只放过音频流上倒退不超过 192 个采样（192 kHz 下 1ms）的；视频流的同类报错、倒退一整帧以上的音频照样算问题。实际踩过一次：一个 FC2 片源有 4 处这样的接缝，12 小时的编码结果因此被丢掉。

### VMAF 抽检

- 段内取**调和平均**而不是算术平均：算术平均会被大量好帧稀释，一段里几十帧崩到 60 分、均值照样 94。调和平均对低分帧敏感得多。段间仍取算术平均和 `vmaf_threshold` 比，但另有一条 `vmaf_min_segment`(90) 的**单段下限**——99/99/81 三段的均值是 93 能过阈值，可那 81 分的十几分钟是看得出来的。设 0 关掉单段下限
- VMAF 抽检是逐帧比对，参考段和待测段错一帧分数就会崩到 30~60 分（画质其实没问题）。为此抽样切点会自动挪到两帧中间：同一帧的时间戳在 mp4（1/24000）和 mkv（1/1000）里精度不同，切点压在帧边界上时两边会一边留、一边丢，整段就错开了。万一还是错了帧（VFR 等异常片源），前后各挪一帧复核，分数能回到正常水平就按对齐后的分数算，并在日志里说明。失败信息会带上每段的位置（如 `53.05@4490s`）方便自己去那个时间点看一眼
- 抽样位置由自适应搜索和这里共用同一段代码算出（`encode.sample_starts`）：均匀铺开、切在帧间隙、片子比样本还短时几段会挤到同一处并自动去重——不去重就会把同一段量五遍，白花时间还让"5 段"的说法名不副实
- **搜索和抽检的段数必须一致**（`[adaptive] sample_count` = `[verify] vmaf_segments`）。两边都以 `(i+0.5)/段数` 分位为中心，段数相同时搜索那 8 秒正好嵌在抽检的 20 秒正中间，量的是同一段内容；段数不同时两组窗口可以完全不相交，"搜索达标"和"抽检达标"说的就不是同一段画面了（实测 4 段 vs 5 段在一部 110 分钟的片子上零重叠，搜索 95.1 而全片抽检 92.2）
- 量不出分数分两种：整个构建没有 libvmaf 只告警放行；有 libvmaf 却在这个文件上失败（抽样写不下去、片段解不开、libvmaf 中途崩掉）一律硬失败——画质是唯一的承诺，量不出来就不能说通过，尤其 `--delete-original` 会跟着删原文件
- 自适应产物按 `target_vmaf` 再复核一次：`vmaf_threshold`/`vmaf_min_segment` 是给固定 CRF 兜底的灾难性失败线，比自适应承诺松得多。抽检的均值或最低段低于目标时打 WARNING、并写进 `results.jsonl` 的 `below_target` 字段，产物仍按通过保留——它过了闸门，但画质欠账不能无声无息，也不该只能靠 grep 日志才查得到

### 色彩与 HDR 比对

`color_check`（默认开）比对 `color_primaries`/`color_transfer`/`color_space`/`color_range` 四项，以及 HDR10 母版信息（mastering display / content light level）、HDR10+、Dolby Vision RPU 是否还在。这项不能交给 VMAF：元数据丢了但像素值不变时 VMAF 照样打 99 分，播放器却会把 BT.2020/PQ 的片子按 SDR 显示，画面发灰——那不是"视觉无损"。源本身没标的项不作要求（编码器补默认值不算退化）。

### 4K 模型

4K 片源会自动换用 `vmaf_4k_v0.6.1` 模型（`vmaf_4k_model = false` 可关掉）。默认模型是按「1080p 屏幕、3 倍屏高」的观看条件训练的，用它量 4K 就是量错了尺子；4K 模型对应「4K 屏幕、1.5 倍屏高」，同样的失真下分数更高（实测同一对文件 95.0 → 97.4），因为那个观看条件下确实更不容易看出来。1440p 这类中间分辨率仍用默认模型。构建里没有 4K 模型时会退回默认模型并打警告——不退回的话 libvmaf 直接报错，会让 4K 文件的画质门槛被整个跳过。自适应搜索和这里的抽检共用这一个开关，两边必须是同一把尺子。

```
    └── test_integration.py  # 真实 ffmpeg 端到端（缺 ffmpeg 自动跳过）
```

模块之间的依赖是单向的：`caps`/`tracks`/`vmaf` 只依赖 `proc`/`util`，`encode` 用 `tracks` 的容器分类，`adaptive` 用 `encode`+`vmaf`，`verify` 用 `vmaf`，`remux` 用 `encode`+`verify`（只做决策与参数生成，编排留在 pipeline）。校验模块不再为了量 VMAF 去依赖编码模块。
